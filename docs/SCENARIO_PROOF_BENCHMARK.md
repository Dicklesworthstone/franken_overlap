# Nested real-scenario proof benchmark

`fo-proof-bench` measures every retrieval method on exactly the same query-document pairs generated by `fo-showcase` or supplied by a manually adjudicated query set.

It is the primary quality/performance experiment for public claims.

## Methods

Each corpus scale compares:

1. normalized exact substring search;
2. character q-gram Jaccard;
3. character q-gram SimHash;
4. fielded BM25 with phrase and proximity evidence;
5. exhaustive semi-global Levenshtein where the declared work budget permits it;
6. FrankenOverlap sparse alignment;
7. unified hybrid retrieval.

Every missing indexed result receives score zero. Exhaustive Levenshtein is different: when a pair is skipped by the cell budget, its score is absent and the query is excluded from exhaustive AUPRC unless every candidate completed.

## Basic run

```bash
cargo run --release -p fo-bench --bin fo-proof-bench -- \
  showcase/gutenberg/sections \
  showcase/gutenberg/queries.jsonl \
  --output benchmark-artifacts/gutenberg-proof.json \
  --scores-output benchmark-artifacts/gutenberg-proof-scores.jsonl
```

SEC:

```bash
cargo run --release -p fo-bench --bin fo-proof-bench -- \
  showcase/sec-10k/sections \
  showcase/sec-10k/queries.jsonl \
  --output benchmark-artifacts/sec-proof.json \
  --scores-output benchmark-artifacts/sec-proof-scores.jsonl
```

## Nested corpus sizes

By default, the benchmark constructs nested candidate universes from:

```text
all required positive documents
10
25
50
100
250
maximum loaded size
```

Sizes smaller than the union of required positives are reported as skipped. Every evaluated size contains every positive used by the selected query set, then adds deterministic distractors. This prevents an apparent speedup from silently deleting hard positives.

Explicit sizes:

```bash
fo-proof-bench CORPUS QUERIES \
  --output report.json \
  --corpus-size 25 \
  --corpus-size 100 \
  --corpus-size 250
```

The candidate-ID list for each size is represented by a SHA-256 digest in the report.

## Timing protocol

For every index size the report separates:

```text
index construction
index serialization
cold index load
first execution of each query
excluded warm-up executions
measured repeat executions
```

Method timing includes:

- first-execution p50 and p95;
- repeat p50, p95, and p99;
- measured operation count;
- total measured wall time;
- operations per second;
- one-shot total cost.

For indexed methods:

```text
one-shot total = build + serialization + cold load + first-query p50
```

For direct methods, one-shot total is the first-query p50.

The report also calculates measured break-even query counts against exact substring and complete exhaustive-Levenshtein retrieval whenever the indexed p95 is lower.

## Quality metrics

Every complete method/query stream reports:

- micro candidate-stream AUPRC;
- macro per-query AUPRC;
- tie-aware expected Recall@1, Recall@5, and Recall@10;
- tie-aware expected MRR;
- nDCG at the configured cutoffs;
- full precision-recall and calibration statistics inherited from `fo-core`.

The same metrics are emitted independently for every scenario profile, so exact-match success cannot conceal OCR, insertion/deletion, fragmented, reordered, or natural-relation failures.

## Span accuracy

Controlled scenarios record the source passage's word offset and length. The benchmark reconstructs its normalized token span and compares it with spans returned by:

- exhaustive Levenshtein;
- FrankenOverlap;
- hybrid overlap evidence, including multiple composite blocks.

Reported span metrics are:

```text
eligible queries
queries with a predicted span
mean and median intersection-over-union
mean expected-span coverage
mean predicted-span precision
mean start absolute error
mean end absolute error
```

`natural_relation` is excluded from exact-span metrics because related editions and filing years do not imply identical local coordinates.

Methods that do not produce alignment spans can still be evaluated for document retrieval, but they cannot establish localization quality.

## Exhaustive work budgets

```bash
fo-proof-bench CORPUS QUERIES \
  --output report.json \
  --maximum-exhaustive-cells-per-query 2000000000 \
  --maximum-exhaustive-cells-per-scale 20000000000
```

The report records, for every query:

```text
complete
evaluated documents
skipped documents
DP cells
elapsed milliseconds
```

No partial run is extrapolated into a fictional full-corpus latency.

## Pair-level receipt

`--scores-output` writes one JSON object per corpus-size/query/candidate combination:

```json
{
  "corpus_size":100,
  "query_id":"CIK0000320193...:ocr_noise",
  "profile":"ocr_noise",
  "source_id":"...",
  "positive_ids":["..."],
  "candidate_id":"...",
  "label":false,
  "scores":{
    "normalized_exact_substring":0.0,
    "character_qgram_jaccard":0.17,
    "character_qgram_simhash":0.55,
    "fielded_bm25_phrase_proximity":0.41,
    "franken_overlap":0.73,
    "franken_hybrid":0.81
  },
  "predicted_spans":{}
}
```

These rows are suitable for paired bootstrap comparisons, hard-negative mining, active learning, fusion tuning, and human review.

## Example focused runs

Only OCR and insertion/deletion profiles:

```bash
fo-proof-bench CORPUS QUERIES \
  --profile ocr_noise \
  --profile insertion_deletion \
  --output noisy.json
```

Retain serialized indexes for inspection:

```bash
fo-proof-bench CORPUS QUERIES \
  --index-root benchmark-artifacts/indexes \
  --retain-indexes \
  --output report.json
```

## Interpreting winners

A defensible result does not require FrankenOverlap to win every workload:

- exact substring should win many exact-query latency comparisons;
- BM25 should be highly competitive on short keyword queries;
- overlap methods should earn their advantage on edited, OCR, fragmented, and reordered specimens;
- hybrid should approach the strongest lane across mixed workloads;
- exhaustive Levenshtein should remain a quality reference only at sizes where it actually finishes.

The generated evidence renderer should state these tradeoffs rather than collapsing them into one unqualified speedup claim.
